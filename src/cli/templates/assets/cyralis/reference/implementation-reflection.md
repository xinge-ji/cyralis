# 写代码时的反射检查

`cs-feat-impl` 和 `cs-issue-fix` 共用。AI 默认会往"大函数 / 大文件 / god class / 处处特殊分支"漂，这一节把漂移截在发生那一刻。

## 最小实现阶梯

写代码时按顺序判断，停在第一个能成立的台阶：

1. **这真的需要存在吗？** 推测性需求直接跳过，并用一句话说明。
2. **现有依赖已经能解决吗？** 已安装依赖能解决就用；几行代码能解决时不新增依赖。
3. **一行能解决吗？** 能一行就一行。
4. **写能工作的最小代码。** 只覆盖当前需求，不为"以后可能"预留接口、配置、文件或抽象。

## 最小实现规则

- 不写未请求的抽象：单实现 interface、单产品 factory、永远不变的配置都不要加。
- 不加"以后用得上"的样板、脚手架、备用路径；以后真的需要时再加。
- 优先删代码，其次复用，最后才新增。新增时用最少文件、最短可工作的 diff。
- 复杂请求先交付懒版本，并在回复里点明覆盖边界：`已做 X；Y 已覆盖。需要完整 X 再说。`
- 两个标准库方案代码量相近时，选边界条件更正确的那个。懒不是选更脆的算法。
- 有意简化但存在明确上限时，用短注释标出来：`# O(n^2) scan, add an index if list size grows`。
- 输出先给代码和结果，再最多三行说明跳过了什么、什么时候再加。不要写未请求的设计说明。

## 结构漂移触发器

**不是阈值，是触发器**——硬数字会诱发为拆而拆把自然聚合的代码切碎。每条都是"遇到 X 情况就停下来问自己"。

| 触发场景 | 停下来问自己 |
|---|---|
| 要往一个已经很长的文件追加代码时 | 文件承担几件事？新加的是已有职责延伸还是第 N+1 件事？是第 N+1 就默认新建文件 |
| 要给已经很多方法的类加方法时 | 新方法是核心职责的自然扩展，还是把类推向"什么都能干"？ |
| 写的函数已超过一屏时 | 函数在做几件事？几件事就拆 |
| 要加 `if (特殊情况) { 特殊处理 }` 分支时 | 抽象维度选错了？正确做法可能是把特殊路径和通用路径分成不同函数 / 策略 / 类 |
| 要 copy-paste 一段代码时 | 能抽成共用还是只字面相似？能抽就抽 |
| 要给函数加第 4+ 个参数时 | 函数做的事是不是太多了？参数列表是 API 恶化的早期信号 |
| 要新写"万能工具类 / helper"时 | 真没归属还是只是想不起来放哪儿就先堆 util？ |

## 停下来之后

反射检查只把问题提出来，结论用户定。停下来想清楚的动作（拆 / 新建 / 重命名 / 抽共用）会让改动超出现有 steps 范围 -> 跟用户对齐再决定（纳入当前推进 / 记顺手发现留后续）。

不许偷偷拆完继续写，也不许忽略信号硬冲。默认动作是停、问、再继续。
